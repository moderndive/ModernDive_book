NoteEX1.1 — show question

EX1.1 (★) A classmate insists “R and RStudio are the same thing — RStudio is just a newer name for R.” In 2–3 sentences, set them straight using an everyday analogy of your choice (car & dashboard, engine & cockpit, kitchen & recipe — whatever clicks for you). Be specific about which one runs the code and which one is the interface you actually click around in.

Solution (reference: Section 1.1 “What are R and RStudio?”).

Answers will vary; an exemplar:

R is the engine; RStudio is the dashboard. R is the actual programming language and the program that runs your code — type mean(x) and R is what computes the answer. RStudio is the wraparound interface you click in: the editor where you write scripts, the console where output appears, the plot pane, the file browser, and the help viewer all stitched into one window. R can work without RStudio (you can run it from a bare terminal), but RStudio has no programming engine of its own.

Other analogies students could go for:
- R is the recipe ingredients; RStudio is the kitchen.
- R is the writing language (English); RStudio is the word processor (Microsoft Word).
- R is the gameplay code; RStudio is the game launcher.

The key idea — separating the language/runtime from the interface — is what matters; the metaphor is just a vehicle for it.

Leftover: 4. factor — none of the listed expressions produces a factor by default. Factors are made with factor() (e.g., factor(c("low", "med", "high"))); we’ll see them more later in the book.

A few subtleties worth pointing out:

  • 3.14 is a double because it has a decimal component. Plain whole-number literals like 42 are also doubles in R by default — even though they look “integer-like” — so the chapter’s mention of int vs. dbl in glimpse() output (Section 1.4.3) refers to how a column is stored, not just how a value looks.
  • c(1, 2, 3) is a numeric vector — every value in R is technically a length-≥1 vector, but here we mean it in the sense the chapter uses: a “series of values” assembled with c().
  • seq() is a function — written with () per the book’s convention for naming functions (Section 1.2.1). Running seq() with no arguments returns 1; passing seq(from = 2, to = 5) returns 2 3 4 5.
  • olympic_athletes is a data frame — class(olympic_athletes) will confirm.

A useful diagnostic in your own work: run class(x) to see the higher-level type of an object.

NoteEX1.3 — show question

EX1.3 (★) Distinguish between an error, a warning, and a message in R. Which of the three halts execution, and which let the rest of your script keep running? Use the chapter’s traffic-light analogy (red, yellow, green) to explain how you should react to each one when you see it in red text in the console.

Solution (reference: Section 1.2.2 “Errors, warnings, and messages”).

  • Error — halts execution. R cannot continue (e.g., calling a function from a package you haven’t loaded yet). 🔴 Red light: stop and fix it — the code didn’t run.
  • Warning — execution continues, but R is flagging something it isn’t fully sure about (e.g., a plot silently dropped rows with missing values). 🟡 Yellow light: the code ran, but slow down and check whether the flag matters for your task.
  • Message — purely informational, nothing went wrong (e.g., the package-loading chatter you see after library(dplyr)). 🟢 Green light: keep going — R is just narrating.

Rule of thumb: red text isn’t always bad. Read the first word — Error, Warning, or neither — to know which traffic light you’re at.

NoteEX1.4 — show question

EX1.4 (★) What’s the difference between library(olympicAthletes) and install.packages("olympicAthletes")? Why do you only need to do one of them once per machine?

Solution (reference: Section 1.3.2 “Package installation” + 1.3.3 “Package loading”).

install.packages() downloads and installs the package files once per machine (think: installing an app). library() loads the package into your current R session (think: opening the app) — required every session.

NoteEX1.5 — show question

EX1.5 (★) Suppose you start a fresh R session and run glimpse(olympic_athletes) without first running library(olympicAthletes) (and without library(dplyr)). What error do you expect, and what’s the fix?

Solution (reference: Section 1.3.3 “Package loading”).

You’ll get could not find function "glimpse" (because dplyr — which provides glimpse() — isn’t loaded). Even if you reach for glimpse()’s namespace, you’d then hit object 'olympic_athletes' not found because olympicAthletes isn’t loaded either.

Fix: load both packages at the top of the session:

library(dplyr)            # provides glimpse()
library(olympicAthletes)  # provides olympic_athletes
glimpse(olympic_athletes)

install.packages() is a one-time per-machine step; library() is a once-per-session step.

NoteEX1.14 — show question

EX1.14 (◆◆) RStudio Projects. A .Rproj file marks a folder as an RStudio Project — opening it sets R’s working directory to that folder, scopes the History panel to it, and (importantly) makes scripts portable across machines because they reference files relative to the project root instead of absolute paths like /Users/yourname/Downloads/....

Create a new RStudio Project for your ModernDive work (File → New Project → New Directory → New Project). Save one script inside it that runs library(olympicAthletes); glimpse(olympic_athletes). Close RStudio, reopen by double-clicking the .Rproj file, and re-run the script. Briefly: what changed about the working directory between the two sessions, and why does that matter when you share code with someone else?

Solution (reference: Extension: RStudio Projects).

Without a Project, R’s working directory is wherever you happened to launch RStudio from — different on every machine, different on every reopen. Inside a Project, the working directory is always the project folder, so read_csv("data/file.csv") works the same for you, for your collaborator, and for the CI machine. The portability of relative file paths is the whole point. Real-world signal that someone is not using Projects: scripts littered with setwd("/Users/specific-person/...").

NoteEX1.16 — show question

EX1.16 (◆◆) View() that works inside Quarto/R Markdown. Base R’s utils::View() errors in non-interactive contexts (when you knit/render a .qmd or .Rmd), which can break documents. moderndive exports a drop-in View() wrapper that behaves identically interactively but in non-interactive contexts renders a DT::datatable() inline instead, so the document still builds. Run View(olympic_athletes) interactively to confirm it opens the usual viewer; then try knitting a Quarto chunk that calls it — observe that the rendered output now shows the data table inline. Briefly: when would you prefer the inline DT rendering over a static printed tibble in a Quarto report?

Solution (reference: Extension: moderndive::View()).

Interactively, moderndive::View() opens RStudio’s standard data viewer (identical behavior to base utils::View()). In a non-interactive Quarto/R Markdown render, utils::View() would error and abort the build; moderndive::View() instead drops a DT::datatable() widget inline. Use the inline DT form when you want a searchable, sortable interactive table that lives inside your rendered report (handy for HTML output where readers might want to filter the data themselves), as opposed to a static printed tibble that just shows the first 10 rows.

NoteEX1.17 — show question

EX1.17 (◆◆) Managing function masking with conflicted. Section 1.3.3 mentioned that loading two packages exporting the same function name (e.g., dplyr::filter and stats::filter) means R silently uses whichever was loaded most recently. The conflicted package turns this silent behavior into a loud error and lets you declare your preferences. Try the snippet above — note how conflicts_prefer() makes the choice explicit. When would you rather have a noisy error than silent overriding?

Solution (reference: Extension: conflicted package).

Without conflicted, the order of library() calls silently determines which version of an ambiguously-named function you get — meaning a small refactor (moving a library() call from the top of a script to a different chunk) can change what your code does. With conflicted loaded, R errors loudly the first time you call an ambiguous function, and conflicts_prefer() lets you make the choice explicit, in writing, where future-you (or a collaborator) can see it. Prefer noisy errors over silent overriding any time correctness depends on which version of the function actually runs — which is essentially always for serious analyses.
