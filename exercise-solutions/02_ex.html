NoteEX2.2 — show question

EX2.2 (★) For each column in olympic_athletes, classify it as numerical or categorical. There are some that look numerical but behave categorically — name at least one and justify.

Solution (reference: Chapter 1, “Identification and measurement variables”).

Numerical: age, height, weight, year. Categorical: sex, team, noc, games, season, city_english, sport, event, medal. Identifier: id, name. Year is interesting — stored as integer, but for grouping/coloring purposes it acts like a small set of categorical levels (every 4 years).

NoteEX2.3 — show question

EX2.3 (★) year stores values like 1896, 2024. Why is treating year as numerical (continuous x-axis on a linegraph) often more useful than treating it as categorical? When would the categorical interpretation be useful?

Solution (reference: Sections 2.4 “Linegraphs” and 2.8 “Barplots”).

Treating year as numerical preserves the ordering and spacing of time, which is what a linegraph needs. Treating it as categorical (factor) can be useful for boxplots or grouped barplots where each Games is its own category to compare side-by-side.

NoteEX2.4 — show question

EX2.4 (★) Build the simplest scatterplot you can: weight (y) vs height (x) on olympic_athletes. When the plot renders, R will print a warning like Removed N rows containing missing values (geom_point). Read the warning and report N. What does that tell you about which athlete-rows have complete bio data — and why might older Games be over-represented in the missing rows?

Solution (reference: Chapter 2 overview, exploring the data).

The plot renders, but you’ll see a warning along the lines of Removed ~70,000 rows containing missing values (geom_point()). That’s the rows where either height or weight is NA — roughly a third of the data set. Bio data wasn’t systematically reported in early-20th-century Games; coverage improved over time but is still incomplete for the most recent Games (athlete privacy and late data ingest). The takeaway: any pattern you see in this scatterplot describes only the subset of athletes with complete bio data, which is not a random sample of all Olympians.

ggplot(olympic_athletes, aes(x = height, y = weight)) +
  geom_point(alpha = 0.05)
Warning: Removed 92382 rows containing missing values or values outside the scale range
(`geom_point()`).

Grammar of graphics

NoteEX2.5 — show question

EX2.5 (★) Run the snippet below. Identify the three pieces of the grammar of graphics at play: the data, the aesthetic mappings (which variable is assigned to which of x, y, and color?), and the geom. Bonus: if you wanted to layer individual points on top of the boxes, which kind of layer would you add?

Solution (reference: Section 2.1 “The grammar of graphics”).

  • Data: olympic_athletes (filtered to sport == "Athletics").
  • Aesthetic mappings (the aes() call): x = sex, y = height, color = sex — sex is mapped to two channels (the x-axis position and the box color).
  • Geom: geom_boxplot() — one box per level of the x variable.

Bonus — layering points on top: add a geom_jitter() (or geom_point() with horizontal jitter) layer:

olympic_athletes |>
  filter(sport == "Athletics") |>
  ggplot(aes(x = sex, y = height, color = sex)) +
  geom_boxplot(outlier.shape = NA) +
  geom_jitter(width = 0.1, alpha = 0.05)

The grammar’s power is exactly this — the boxplot and jittered points share the same data and aesthetics, so they line up automatically.

Solution (reference: Section 2.3 “Scatterplots”, grammar of graphics layers).

Good labels turn a chart from “data” into a communication artifact. A reader who sees only the image — not your code — needs to know what’s plotted, in what units, and where the data came from.

olympic_athletes |>

NoteEX2.24 — show question

EX2.24 (★★) A single boxplot for all sports would have hundreds of boxes. Why is filtering to a few sports a better visualization choice than showing them all?

Solution (reference: Section 2.7 “Boxplots”, chart legibility).

Visual clutter masks the signal. With 50+ boxes, individual medians are unreadable, axis labels overlap, and the chart conveys “lots of sports” instead of any specific comparison. Selecting a small set lets the reader actually compare.

NoteEX2.25 — show question

EX2.25 (★★★) A boxplot of weight for one sport shows many “outlier” dots above the upper whisker. Are these necessarily data errors? Justify in 1–2 sentences.

Solution (reference: Section 2.7 “Boxplots”, IQR rule).

No. Boxplot “outliers” use the \(Q_3 + 1.5 \times \text{IQR}\) rule and flag any unusually large value relative to the bulk — but heavyweight sports legitimately produce athletes well above average. They’re statistical outliers, not necessarily errors.

NoteEX2.29 — show question

EX2.29 (★★) Filter olympic_athletes to year == 2024 & season == "Summer". Build a geom_bar() of athlete-rows by medal. The NA bar dominates — why? (Hint — think about what fraction of athletes at any Games win no medal in any event.)

Solution (reference: Section 2.8 “Barplots”, geom_bar counts internally).

The NA bar dwarfs the medal bars because at any single Games, the vast majority of athletes who compete don’t end up on a podium — only the top three per event get a medal, but every roster member of every team gets a row in olympic_athletes. The medal bars themselves should be roughly equal in size (each event awards one gold, one silver, one bronze).

Solution (reference: Section 2.8 “Barplots”, geom_bar() vs `geom_col()).

geom_bar() counts rows — exactly what we want here (no pre-tallying needed). geom_col() requires a pre-computed y value.

NoteEX2.31 — show question

EX2.31 (★★★) A pie chart of the top-10-NOC medal totals from EX2.27 would be visually appealing. Give two reasons the chapter argues a barplot is better.

Solution (reference: Section 2.8 “Must avoid pie charts!”).

  1. Humans judge length more accurately than angle: differences between similar-sized slices are nearly impossible to perceive. (2) Sorted bars convey ranking at a glance, while pie slices need a legend or numeric labels for the same effect.
NoteEX2.32 — show question

EX2.32 (★★) On olympic_athletes, rebuild your EX 2.28 plot but switch from the default stacked bars to side-by-side bars with position = "dodge". What’s easier to see in the dodged version that was harder in the stacked one?

Solution (reference: Section 2.8 “Barplots”, dodged bars).

In the stacked version (EX 2.28), male and female totals sit on top of each other within a single bar, so it’s hard to read the absolute count of each separately. Dodging puts the male and female bars side by side inside each season, making the per-sex absolute counts directly comparable across the four bars.

ggplot(olympic_athletes, aes(x = season, fill = sex)) +
  geom_bar(position = "dodge")
NoteEX2.33 — show question

EX2.33 (★★) Take your EX 2.28 stacked barplot of athlete-rows by season filled by sex, and switch the geom_bar() argument to position = "fill". Now each season’s bar reaches 100 %. Compare the two charts: what new question does the proportional version answer (that the stacked-counts version cannot), and conversely what does the stacked version show that gets hidden when you switch to proportions?

Solution (reference: Section 2.8 “Barplots”, position = "fill").

ggplot(olympic_athletes, aes(x = season, fill = sex)) +
  geom_bar(position = "fill")

What the proportional version answers (that the stacked-counts version cannot): what share of each season’s athletes are male vs. female? Both bars now reach 100 %, so the relative balance is directly readable on the y-axis.

What the stacked version showed (and the proportional version hides): the absolute count of athletes per season — i.e., that Summer has many more athletes than Winter to begin with. After position = "fill", the two seasons look like equally tall bars, regardless of how many athletes each Games actually had.

Counts answer “how many?”; proportions answer “what share?”. Different questions, different geom configurations.

Critical thinking and open exploration

NoteEX2.34 — show question

EX2.34 (★★★) Imagine a news outlet posts a chart of “USA’s medal dominance” using a y-axis that starts at 50 (cropping the bar baseline). Explain in 2–3 sentences how the chart misleads viewers, and what a more honest chart would look like.

Solution (reference: Section 2.8 “Barplots”, chart honesty).

Cropping the y-axis exaggerates differences — a USA total of 120 vs a peer’s 90 looks like 4× as many (70 vs 40 above the cropped origin) instead of the true 1.33×. An honest version starts the y-axis at zero, or uses a non-bar geom (e.g., points + connecting line) where a non-zero baseline is conventionally acceptable.

NoteEX2.40 — show question

EX2.40 (◆◆) Themes. ggplot’s default look isn’t the only option. Try theme_minimal(), theme_bw(), and theme_classic() on the basketball scatterplot from EX 2.6. Which would you reach for in a printed report vs. a slide deck? Why?

Solution (reference: Extension: ggplot themes).

theme_minimal() strips the gray panel background and most gridlines — clean for printed reports where heavy ink wastes paper. theme_classic() adds axis lines only (no gridlines, no background) — great for slide decks where you want maximum data-ink ratio at low resolution. theme_bw() keeps faint gridlines but drops the gray panel — a good general-purpose default. The default theme (theme_gray) is fine for exploratory work but looks dated in polished output.

NoteEX2.42 — show question

EX2.42 (◆◆) Saving plots to file. ggsave() saves the last plot (or a named plot object) to disk in your preferred format and dimensions. Save a histogram of age as a 6-inch × 4-inch PNG at 300 DPI. Then save the same plot as a PDF. Which format is better for inclusion in a printed report? In a website? Why?

Solution (reference: Extension: ggsave).

ggsave("age_hist.png", p, width = 6, height = 4, dpi = 300) writes a 6 × 4-inch PNG at print resolution.

  • PNG is a raster format (a grid of pixels). Good for the web (small files, broad browser support) but quality degrades when scaled up beyond its DPI.
  • PDF / SVG are vector formats (a list of shapes). They scale arbitrarily without quality loss — essential for printed reports, journal submissions, and posters.

Rule of thumb: PDF for print, PNG (or SVG) for web. The same ggsave() call works for both — just change the extension.

NoteEX2.43 — show question

EX2.43 (◆◆) Annotating plots with annotate(). Use annotate("text", ...) and annotate("rect", ...) to draw the reader’s eye to a specific cluster in the Height-vs-Weight scatter — for example, the basketball-center region (≥ 200 cm tall, ≥ 100 kg). Briefly: what’s the difference between annotate() and geom_text() for labeling individual points?

Solution (reference: Extension: annotate()).

annotate(...) places a single label/shape at fixed coordinates — useful for guiding the reader’s eye to one specific region (a cluster, an outlier, a threshold line). geom_text(aes(label = name)), by contrast, draws one label per data row — useful when every point deserves its own label (small datasets only — anything bigger than ~30 points gets unreadable). For the basketball-centers callout, annotate() is the right tool: one label for the region, not one label per athlete.

NoteEX2.49 — show question

EX2.49 (◆◆◆) ylim() vs coord_cartesian(). Both restrict the y-axis range — but ylim() removes points outside the range before statistics like geom_smooth() run, while coord_cartesian(ylim = ...) zooms the view after statistics run. Run the comparison above. Why does the smoother differ between the two panels?

Solution (reference: Extension: ylim vs coord_cartesian).

ylim(50, 120) removes the rows with weight outside [50, 120] before any stats run, so geom_smooth() fits to a subset of the data. coord_cartesian(ylim = c(50, 120)) keeps all rows in the fit and just zooms the visible window afterward. The smoother in the trimmed version is fit on fewer (and skewed) data; the smoother in the zoomed version reflects the full dataset’s structure. Almost always you want coord_cartesian() — trimming silently changes what your statistics describe.
